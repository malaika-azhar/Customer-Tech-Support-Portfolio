<a id="project-background"></a>
## 📖 Project Background

"Offline" only says Windows cannot reach the printer. The cause can be power, cable, a changed network address, a stuck spooler, or a driver problem. Guessing wastes time and can leave the real cause in place. This lab works from the simplest check to the most complex one.

- **Module 1 — Issue Identification:** Rule out power and network before touching software.
- **Module 2 — Resolution & Verification:** Fix the spooler, then the driver if needed, and prove it from another user's PC.
- **Module 3 — Customer Interaction:** Handle a department-wide problem involving sensitive documents.

> [!NOTE]
> The affected documents are financial reports. Jobs stuck in the queue may print all at once when the printer comes back, so watch the output tray.

> [!NOTE]
> **How this lab was really run:** I had no physical network printer, so I built a test printer called `Finance-Printer` on one Windows PC. It uses the built-in "Generic / Text Only" driver on a TCP/IP port that points to `10.255.255.250`, an address with no device on it. This made the printer fail on purpose. The fault I created is a dead port address, and Windows showed it as **"Error"**, not "Offline".

<a id="module-1"></a>
## 🔵 Module 1 — Issue Identification

**Objective:** Rule out hardware and network causes before changing software.

### Step 1 — Check power and cable (described, not tested)

Confirm the printer is on and the network or USB cable is connected. My lab printer is virtual, so there was no power or cable to check.

### Step 2 — Check the network address and offline setting ✅ (partly tested)

- Ping the printer's IP address (described, not tested: I did not run `ping`). A printer whose IP changed will show "Offline" even when it is on.
- Check the "Use Printer Offline" setting in the printer menu. I tested this on a first test printer (Microsoft Print To PDF). The setting showed `WorkOffline = True`, but the printer ignored it and still asked where to save each job, so I could not use it as the fault.
- I then built `Finance-Printer` on a port with an unreachable address and sent two test jobs: "Q3 Financial Report - page 1" and "Q3 Financial Report - page 2".

<p align="center">
  <img src="screenshots/Exhibit1_printer_offline_status.png" alt="Exhibit 1 - printer status Error" width="850"><br>
  <em>Exhibit 1 — Finance-Printer selected in Devices and Printers. Status shows "Error". Computer name hidden with a black box.</em>
</p>

🎯 **Result:** The printer shows a fault and does not print. In this lab the cause is a port that points to an address with no device. Windows showed **"Error"**, not "Offline".

| Check | Result |
|---|---|
| Power status | Described, not tested (virtual printer) |
| Network/USB cable | Described, not tested (virtual printer) |
| Printer reachable by IP | Described, not tested (`ping` not run). The port address was set to `10.255.255.250` on purpose |
| "Use Printer Offline" | Tested on a first printer: set to True, but the printer ignored it |
| Conclusion | Port address with no device behind it. Status shown as "Error" |

<a id="module-2"></a>
## 🟢 Module 2 — Resolution & Verification

**Objective:** Fix one thing at a time and prove the fix from a user's point of view.

### Step 3 — Restart the Print Spooler ✅

Open `services.msc`, find "Print Spooler" and restart it. This clears stuck internal queue state.

<p align="center">
  <img src="screenshots/Exhibit2_print_spooler_restart.png" alt="Exhibit 2 - restart print spooler" width="850"><br>
  <em>Exhibit 2 — Print Spooler shown as "Running" in <code>services.msc</code> after the restart</em>
</p>

I did not record the printer status right after the restart. The screenshot shows the service running, not the result on the printer. The fault was only cleared later in Step 7, so the restart was not the fix in this lab.

### Step 4 — Check stuck jobs ✅ (release with the owner: described, not tested)

I looked at the print queue and found my two test jobs waiting, one with status "Error - Printing". In Step 7 I deleted both jobs with `Get-PrintJob -PrinterName "Finance-Printer" | Remove-PrintJob`. Asking the owner whether to release or cancel real financial reports is described, not tested.

### Step 5 — Check driver and firmware versions ✅ (driver listed; firmware: described, not tested)

I opened Print Server Properties (`printui /s /t2`, Drivers tab). It lists "Generic / Text Only" as installed (x64, Type 3 - User Mode). This window has no version column, so I did not compare versions. Comparing the driver with printer firmware is described, not tested: a virtual printer has no firmware.

<p align="center">
  <img src="screenshots/Exhibit3_driver_update.png" alt="Exhibit 3 - driver check" width="850"><br>
  <em>Exhibit 3 — Print Server Properties, Drivers tab. "Generic / Text Only" is installed. This is a driver check only, no update was done. Computer name hidden with a black box.</em>
</p>

### Step 6 — Install the updated driver (described, not tested)

Download the driver only from the manufacturer's official page. Install it on the machine that shares the printer, and on client PCs if they need it. I did not do this. The lab driver is built into Windows and the fault was not a driver problem.

> [!IMPORTANT]
> Restart the spooler first and test. If that fixes it, a driver update was not needed, and you cannot claim the driver was the cause.

### Step 7 — Repoint the port and send a test print ✅

This was the step that fixed the fault. I deleted the stuck jobs, moved the printer from the dead TCP/IP port to `PORTPROMPT:`, and sent a new test job:

```
Get-PrintJob -PrinterName "Finance-Printer" | Remove-PrintJob
```
```
Set-Printer -Name "Finance-Printer" -PortName "PORTPROMPT:"
```
```
"Q3 Financial Report - test" | Out-Printer -Name "Finance-Printer"
```

A "Save as" box appeared and I saved the output as a file. That shows the job now reaches the output.

<p align="center">
  <img src="screenshots/Exhibit4_test_print_ready.png" alt="Exhibit 4 - after the fix" width="850"><br>
  <em>Exhibit 4 — After the fix: Finance-Printer shows "0 document(s) in queue" and no error. Computer name hidden with a black box.</em>
</p>

The screenshot does not show the word "Ready", and it does not show the saved test file.

### Step 8 — Test from another user's PC (described, not tested)

A test print from the admin PC is not enough. The department must be able to print. I tested on one PC with one account only.

🎯 **Result:** The printer left the error state and the queue was empty. The test job reached the "Save as" box on the same PC.

| Check | Result |
|---|---|
| Test print | Reached the "Save as" box on the same PC ✅ |
| Printer status | "0 document(s) in queue", no error (not "Ready") ✅ |
| Test from another user's PC | Described, not tested |

**Objective:** Restore printing for a department and be honest about what was tested.

> *"Our whole department can't print financial reports."*

**Agent response given:**
- **During the fix:** "I understand the department is blocked. I'm checking the printer now."
- **After the fix:** "The printer is back online and a test print worked from another user's PC. Please print one report to confirm. If any old jobs were waiting, I'll check with you before they print, since they are financial reports."

> [!NOTE]
> **Described, not tested.** This is a scripted scenario. There was no real customer. In my run the test print was on the same PC, so the sentence "worked from another user's PC" is what the agent would say after doing that test.

<a id="scope-limitations"></a>
## 🚧 Scope & Limitations

- **Virtual printer only:** There was no physical network printer. Power, cable, `ping` and firmware checks are described, not tested.
- **Fault was created on purpose:** The cause was a port pointing to an address with no device. This lab does not prove what breaks a real department printer.
- **Status was "Error", not "Offline":** Windows did not show the word "Offline" for this fault. The first attempt with "Use Printer Offline" did not hold jobs on Microsoft Print To PDF.
- **Spooler restart result not recorded:** I did not note the printer status right after the restart. Only the later port change cleared the fault.
- **Driver update described, not tested:** I only checked the driver list. The Print Server Properties window had no version column, so I did not compare versions.
- **Another user's PC described, not tested:** Everything was done on one PC with one account.
- **Queued jobs deleted, not released:** The "release with the owner present" step is described, not tested.
- **Exhibit 4 shows "0 document(s) in queue", not "Ready"**, and does not show the saved test file.
- **Exhibit 5 was taken before the spooler restart**, because the queue changes once the fault is fixed.
- **Private data hidden:** Computer name and queue owner are covered with solid black boxes in the screenshots.
- **Cleanup:** At the end I removed the lab printer (`Remove-Printer`), the port `IP_10.255.255.250` (`Remove-PrinterPort`) and the folder `C:\Temp`. `Get-Printer` then returned "No MSFT_Printer objects found".
- **Print server setups are not covered.** If a print server shares the printer, the driver must be updated there.

<a id="what-i-learned"></a>
## 🧠 What I Learned

- **"Offline" is a symptom.** Power, network address, spooler and driver are all possible causes. A dead port address showed up as "Error" in my lab.
- **Start with the cheapest check.** Restart the spooler before changing drivers. In my lab the restart was not enough, which is why I could say the cause was the port and not the driver.
- **Fix one thing at a time.** Otherwise the cause stays unknown.
- **A lab can fail in unexpected ways.** My first offline setting was ignored by the printer, so I had to change the lab setup.
- **Sensitive jobs need care.** Queued reports can print unattended when the printer returns. I deleted my test jobs, so I did not see this happen.
